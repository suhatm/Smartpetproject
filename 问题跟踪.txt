【问题 #001】断 J-Link 的 USB 与断 4 根连接线效果不一样（"拔 J-Link 板子就死"）
--------------------------------------------------------------------------------
状态：待实验最终验证（机理已明确，见下）
发现日期：2026-09-30
现象：
  - 拔掉 J-Link 的 USB 线（4 根杜邦线仍留在板上）→ 板子"死"（无心跳）；
  - 拔掉板侧 4 根杜邦线（J-Link USB 仍插着）→ 板子正常（心跳持续闪）；
  - 逐根拔 SWD 线（单变量实验）→ 每根都不影响运行；
  - 只接电池、完全脱离 J-Link → 板子完全正常。
机理分析（高度怀疑为根因）：
  本机探针为 STM32F072 方案的 OB 克隆 J-Link。断 USB 后探针自身失电，
  其每个 I/O 脚内部的 ESD 保护二极管仍连接到探针自己的 3.3V 电源轨：
    - USB 插着（探针有电）：引脚正常驱动，nRESET 被探针维持高电平 → 板子活；
    - USB 拔掉（探针失电）  ：板子 nRESET（内部 13kΩ 上拉到 3V）的电流经
      探针 ESD 二极管倒灌进失电的探针电源轨，把该轨充到中间电位，
      nRESET 被钳位到约（轨压 + 0.6V），可能低于 SoC 的 VIH →
      芯片被按在复位态 → "板子假死"。
  GND 线仍连接，为寄生电流提供了回路；SWDIO（SoC 内部上拉）同样在
  向失电探针灌电，加剧钳位效应。
待做的决定性实验：
  1. 4 根线全接、USB 插着，确认心跳在闪；
  2. 只拔 J-Link 的 USB 线（板侧 4 根线不动）；
  3. 预期若 20s 内心跳消失 → 机理实锤；重新插回 USB 后应观察到
     "红闪 3s + 双闪 3s" 完整重启序列（芯片从复位态释放后重新 boot）。
规避措施（无论实验结果如何均建议执行）：
  - 调试收工时：先拔板侧 4 根线，再拔探针 USB（顺序不能反）；
  - 或者只断开 RESET 那一根线，探针 USB 可以一直插着；
  - 量产无影响：产品上没有探针，该问题仅限调试场景。
对已有结论的影响：
  - 板子硬件与固件本身零缺陷（纯电池独立运行已验证正常）；
  - 之前"拔 J-Link 就死"的所有观测，均可用本机理解释；
  - 验证记录《上板验证记录-电源UI固件.md》§7 的"结案"结论需要按本问题
    实验结果修订（误判的根因从"Ship 态短按无反应+灯效太短"修正为本机理）。

【问题 #002】nPM1300 OTP 冷启动默认 Active（插电池即开机）——运输耗电风险
--------------------------------------------------------------------------------
状态：待产品决策

  a) 出厂前产线工位手动长按关机进 Ship（零改动，靠流程保证）；
  b) 用 nPM PowerUP 修改 OTP，把默认态改为 Ship（硬件层面保证，需烧 OTP）。
备注：当前阶段样机调试期间此行为反而方便（插电池即活）。

【问题 #003】LED2（蓝）原理图网表层面极性存疑（实物正常）
--------------------------------------------------------------------------------
状态：实物已验证正常，原理图层面留档
结论：实板蓝灯可正常点亮（关机蓝闪、短按确认均可见）。网表分析判"接反"
      是符号库（MHT192DBCT pin1=K）与实物引脚定义差异造成的误判。
建议：下一版原理图选型时统一 LED 符号库极性定义，或改用双向/双色管，
      避免 DRC 阶段再次误报。
附带事实：蓝灯 Vf 2.5~3V，Buck1 未使用（VSYS≈VBAT 3.0~4.2V），
      电池电压低于约 3.3V 时蓝灯会变暗——低电量场景"关机蓝闪"可能偏暗，
      后续若需要可换低 Vf（≤2.6V）蓝灯。

【问题 #004】NCS v3.4.0 复用 build 目录增量编译会失败（SDK 层坑）
--------------------------------------------------------------------------------
状态：已明确规避方法
现象：非 pristine 的增量编译（ninja -C build 或 west build 复用目录）触发
      nrf_security 模块 Kconfig malformed 赋值报错中止
      （CONFIG_MBEDTLS_CONFIG_FILE 空值 cache 变量被回喂 Kconfig）。
规避：一律使用 `west build --pristine`（约 13 分钟），增量调试期改用
      ninja 时需注意此坑。

【问题 #005】烧录后 RTT 无输出：旧固件残留的满缓冲区跨复位存活
--------------------------------------------------------------------------------
状态：已明确规避方法
现象：烧新固件后 RTT 读不到新日志（WrOff 卡在 0x3FF）。
根因：.rtt_buff_data 为 NOLOAD 段，旧固件写满的 RTT 控制块跨复位存活；
      SEGGER RTT 惰性初始化检测到合法 ID 就跳过重置，SKIP 模式丢弃新日志。
规避：烧录后用 SWD 清零控制块首字再复位：
      nrfutil device write --address 0x20000470 --value 0 --direct
      然后 nrfutil device reset。

【问题 #006】GUI 上位机：J-Link V9.24a 错误弹窗（TLE9863QXW20）+ 窗口未响应
--------------------------------------------------------------------------------
状态：已修复（f0e3360 + 器件包清理 2026-09-30）
发现日期：2026-09-30（GUI 首次使用时）
现象：
  - 测试时反复弹出 "J-Link V9.24a Error: Device TLE9863QXW20:
    Flash bank 0x11000000: No loader specified"；
  - GUI 窗口标题出现"(未响应)"。
根因（两个独立问题）：
  1) 弹窗：上位机 write 命令未带 --family 参数 → J-Link DLL 需要设备
     信息 → GUIServer 弹设备选择框，默认指向器件包中的损坏条目——
     %APPDATA%\SEGGER\JLinkDevices\HDSC-JLinkDevices.xml 注册了
     TLE9863QXW20（Flash bank 0x11000000），但其 loader 文件
     Devices/Infineon/TLE986x/TLE9863.FLM 不存在 → 每次连接必报错。
  2) 冻结：GUI 状态轮询跑在 Tk 主线程（root.after 回调内做阻塞
     subprocess 调用），单次 SWD 读可达数秒 → 主循环被卡住。
修复：
  1) write 命令统一加 --family nrf54l（显式指定器件族，DLL 不再弹框）；
     并移除器件包中损坏的 TLE9863 条目（备份：
     HDSC-JLinkDevices.xml.bak-20260930）；
  2) GUI 重构线程模型：全部 nrfutil 调用只在后台线程执行，UI 更新经
     queue 投递回主线程 100ms ticker，主线程零阻塞。
验证：
  - GUI 重启后 20s 无弹窗、无 JLinkGUIServer 进程、无报错日志；
  - 连续运行稳定性实测（2026-09-30）：GUI 连续运行约 5 分钟正常关闭退出，
    gui_log.txt 全程无异常输出、无崩溃堆栈——线程模型修复在实际使用中稳定有效。

【问题 #007】BLE 断开后广播重启失败 rc=-12：断开一次即无法再连接
--------------------------------------------------------------------------------
状态：已修复（task-V1.02，2026-10-01 上板复验通过）
发现日期：2026-10-01（BLE LED 测试首轮上板，RTT 日志实锤）
现象：
  - 手机连接后断开（reason=0x13），RTT 记录 BLE,adv_start_failed,rc=-12；
  - 之后手机扫描再也找不到 SmartPet，直到整机关机重启才恢复广播；
  - 用户第二轮"测试成功"正是靠关机重启规避了此问题（当时未察觉）。
根因：
  disconnected 回调（BT RX 线程上下文）里同步调 bt_le_adv_start，
  此时控制器尚未释放连接资源 → 返回 -ENOMEM(-12)。
修复（src/bluetooth/ble_led_service.c）：
  - 广播重启改为 K_WORK_DELAYABLE 延迟 20ms 投递到系统工作队列；
  - 失败自动以 100ms 间隔重试（最多 5 次）；
  - ble_led_test_shutdown() 先置 shutting_down 标志并 cancel 延迟工作，
    避免关机停广播后又被工作项复活（与断开回调同构互斥）。
验证：
  重烧后连接→断开→RTT 应记录 BLE,adv_started（不再 -12），
  手机可立即重连。回归：关机时 BLE,adv_stopped 时序不变。

【问题 #008】RTT 上行缓冲 1KB 过小：单轮 BLE 测试即写满丢日志
--------------------------------------------------------------------------------
状态：已修复（CONFIG_SEGGER_RTT_BUFFER_SIZE_UP=4096，task-V1.02）
发现日期：2026-10-01
现象：开机 banner+自检+BLE 初始化日志约 1KB，首轮测试中缓冲写满
      （WrOff=0x3FF），此后所有 BLE 事件日志（含用户成功的 led_write
      记录）被 NO_BLOCK_SKIP 静默丢弃，只能靠肉眼现象复盘。

附带发现：清 acID 复位后新日志起点并非缓冲 0 偏移（残留前段旧字节，
      读日志时以最后一处 "*** Booting" 为界解析即可，不影响使用）。

【问题 #009】静电 B（QVAR-B/U4）恒灰无反应：U4 驱动 device_init 的 sw_por 清掉 CTRL7
--------------------------------------------------------------------------------
状态：已修复（task-V1.10，待上板复验）
发现日期：2026-10-05（上位机截图：静电 A 绿、静电 B 灰且值恒"—"，REPROBE 无效）
现象：
  - 开机后上位机"静电 B (U4)"灯恒灰、数值"—"，QVAR-B 波形无输出；
  - 静电 A（U1）正常；主板 U4 六轴照常出数；
  - 按"重新探测外设"(CMD 0x06 QVAR) 也无法恢复。
根因（启动时序竞态，静态代码实锤）：
  1. 开机 4.10 qvar_bringup_test 裸 I2C 置 U1/U4 CTRL7.ah_qvar_en=1，
     双通道 ACTIVE（此时 B 自检还能过）；
  2. 上位机连接后 imu_stream_start() 对 U4 做首次 device_init()
     （overlay deferred-init），NCS v3.4.0 驱动 init_chip() 在 I2C
     分支必走 lsm6dsv16x_sw_por()（lsm6dsv16x.c:1363）→ U4 全部
     寄存器复位，CTRL7.ah_qvar_en 被抹掉，驱动只重配 XL/G；
  3. 从此 U4 STATUS.ah_qvarda 永不置位 → qvar_read_one(B) 每帧
     -EAGAIN（不计 io_fail）→ 通道卡"僵尸 ACTIVE"（状态仍 ACTIVE、
     帧级 st=PRESENT），0x03 帧 b_valid 恒 0；
  4. U1 无此问题：body_imu（4.9）的 device_init 早于 QVAR 使能（4.10）；
  5. qvar_channel_reprobe() 对 state==ACTIVE 盲目短路返回 0，REPROBE
     空转；QVAR_CFG(0x05) 能强重配但上位机无入口。
  同病根场景：PWR_SET SENS 关→开后 sensor_hub_bridge 的恢复路径调
  qvar_channel_reprobe(A/B) 同样被 ACTIVE 短路，A/B 双双僵尸。
修复（task-V1.10）：
  - qvar_sensor 新增 qvar_channel_reconfigure()：无条件全序列重配；
  - imu_stream.c device_init(U4) 成功后立即 reconfigure(QVAR-B)；
  - body_imu.c device_init(U1) 成功后 reconfigure(QVAR-A)（兜底）；
  - qvar_read_one 连续 EAGAIN 达 90 帧（30Hz 约 3s）自动重配自愈
    （QVAR,data_stale,reconfig 日志）；
  - qvar_channel_reprobe 的 ACTIVE 分支改为回读 CTRL7 校验 ah_qvar_en，
    链没了落到全序列重配（治好 SENS 关→开恢复路径）。
协议与上位机：无需改动（§6.3 6B 帧 + valid 位图语义正确，上位机如实显示）。
验证方法（上板）：连接上位机开流后看 RTT，应出现 IMU_STREAM,started 后
  紧跟 QVAR,B,enabled（reconfigure 生效）；上位机静电 B 转绿、波形随
  触碰 B 电极波动；RTT 若出现 QVAR,x,data_stale,reconfig 说明自愈触发。

【问题 #010】（预留编号）
